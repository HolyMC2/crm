# CRM acceptance contract

Approved roadmap execution: 2026-09-26. User decision: product name **CRM**. The prior Ronda/other-name proposals are superseded. A distinct icon and consistent CRM identity remain in scope.

User requires the complete roadmap and final approval by **Claude Opus 5.5**. This document defines the gates before implementation results are judged. It cannot be weakened after a failure merely to obtain approval.

## Verdict rule

The only final verdicts are **READY** and **NOT_READY**. READY requires every mandatory gate below to pass on the final assembled revisions, and an independent Opus 5.5 review of the exact code/evidence to say READY. A missing test, inaccessible provider, skipped mandatory scenario, incomplete route, placeholder API, stale CI result, unverified migration or unresolved material finding means NOT_READY.

A package may be complete while the overall roadmap remains NOT_READY. Do not describe interim package review as final approval. No weighted score, average or percentage overrides a failed gate. Existing mandatory-path bugs count even when they predate this task.

Severity: S0 = disclosure/corruption/unauthorised effect/money error; S1 = broken required journey, duplicate/lost work, permission or source-of-truth defect; S2 = mandatory UX/accessibility/performance/configuration requirement failure. READY permits zero unresolved S0/S1/S2 in the accepted scope. Cosmetic observations outside that scope may be recorded with explicit rationale.

## Evidence format

Every gate has requirement ID, tested source SHA(s), environment/image and installed-app set, actor/scope, setup, exact command or browser scenario, expected/observed result, artifact location and reviewer finding status. Historical receipts establish baseline only. Separate test doubles from native database/browser/provider proof.

Store raw local evidence under `~/muelle-releases/crm-roadmap-20260926/`. Keep credentials, session state, customer content and private tenant data out of Git/public artifacts. Retain full migration logs privately; publish only sanitised summaries. Evidence manifest identifies which commit each result covers; later relevant changes invalidate affected results.

## Review procedure

1. Primary freezes these gates and keeps the execution ledger current. Opus may strengthen or clarify them; any scope change is recorded with justification.
2. Builders own disjoint files and supply evidence. Primary inspects diffs and runs integration checks; builder assertions are not acceptance.
3. Opus performs an early contract/architecture challenge to catch false independence, overlapping state ownership and untestable criteria.
4. After implementation, primary assembles reproducible final code/test/migration/browser/performance/provider evidence and records exact SHAs.
5. Fresh Opus final review reads the code and evidence independently. It returns JSON with model, revision map, verdict, gate results, severity-tagged findings and reproduction pointers. No conditional READY.
6. Fix every blocking finding, rerun affected checks and obtain a new final review for the new revisions. Do not reuse an approval across changes.
7. Release/activation evidence is checked separately from code readiness. If a live credential/account or external effect requires user input, finish independent work and mark that exact gate unproven rather than silently reducing scope.

## Scope decisions

- Product name CRM is final for this work; use a distinct icon, not a new product name.
- User selected Mercado Libre, then explicitly prioritised Facebook and WhatsApp catalog/marketplace first. Meta catalog commerce is the first integration package; Mercado Libre remains subsequent scope. API/account limitations require an explicit supported handoff and honest capability state, never a fabricated Facebook Marketplace connector.
- Sales configuration is included with its feature, never postponed as a last-phase checkbox.
- Source history and reusable contracts remain; no replacement database, finance ledger, order engine, customer inbox or automation runtime.
- Complete implementation/verification is authorised. Preserve unrelated work and run integration in task-owned disposable/lab environments. Existing environment guards and outward-effect authorisation still apply.

## Meta contract challenge: actual Opus 5.5, 2026-09-26

- **F01/F05/F06:** inventory every customer-facing catalog/menu/Flow send. Retire direct transports or route through the native outbox; wrong default-account fallback is forbidden. Define bounded catalog/product/product-list schemas, dedicated action identity, immutable catalog-binding evidence and queue/dispatch revalidation without changing old intent fingerprints. Interactive catalog sends require an open service window; outside it, an approved template and its correct consent purpose are required, otherwise disable with an explanation. - **F02/F03:** the same release disables old auto-order creation and makes old queued order jobs harmless. A signed receipt atomically creates one review intake with zero automatic orders. Inject crashes before consumer execution, after intake before receipt completion, during order creation and after commit; recovery must not lose or duplicate work. - **F04/F07:** intake identity includes authenticated provider/app/account/message, preferably the receipt event key, and links the canonical conversation. Unknown/unpublished/unpriced item, wrong catalog, wrong currency, invalid/over-cap quantity, too many lines, insufficient stock and ambiguous pricing block creation.
